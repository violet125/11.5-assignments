# 招商需求与空间匹配 Agent

## 行业分析对应的建设方向

依据用户提供的行业分析报告截图，本项目聚焦招商需求在交接过程中丢失的问题。报告定位了三个断点：面访时硬件诉求未落库、交接无字段校验、退回无痕。各节点耗时尚未分别测量，因此不将任何环节断言为"最耗时"。

业务流程：线索 → 需求访谈 → 空间匹配 → 报价 → 合同审核 → 交付。本项目当前范围为需求访谈、空间匹配、交接校验、复核闭环与报价单草稿（v2，含编号版本、三年总占用成本、让利授权审批）；合同审核与交付只预留接口，不属于已实现功能。

### 验收目标与前置条件

- 报告中的一级验收目标：需求交接遗漏率从 22% 降至 8%。这属于报告基线与目标，不是本原型已经取得的效果。
- 意向转访率 31% → 45% 仅作为观察指标，不作为本项目验收依据。
- 试点前需确定遗漏率的统计单位、分母、抽样范围、时间窗口和复核责任人，并复核 22% 基线；不能用字段填写率替代交接遗漏率。
- 房源载体参数台账必须由业务及工程人员建设和核实，开源软件不能替代真实数据采集。
- 报告提及六项尚未核实的组织与流程前提，但当前截图未展示完整清单，不能将其视为已经满足，需依据原报告补齐。
- 报告要求的专业确认独立留痕、审批人不可代劳、脱敏与授权可见，已在本项目实现为代码约束（见下文），但真实登录与身份认证体系尚未接入。

### 业务模块与当前实现状态

1. **需求结构化**：从访谈原文提取面积、租金、硬件诉求并保留原文证据。层高、净高、电力容量、承重、配电冗余分别建字段。空白的四种业务语义（已明确 / 未知待补 / 未提出要求 / 确认无此要求）由 `state` 字段显式区分，冲突描述提交人工处理。**已实现。**
2. **载体参数台账**：按园区、楼栋、楼层、房源管理参数，记录单位、适用范围、资料来源、核实人、核实日期及版本。层高不能替代净高，设备功率 kW 不能直接替代供电容量 kVA。溯源信息不完整的房源不会被判为"满足"。另设六个仅用于报价的参数（得房率、物业费、交付标准、净高、供电冗余、空调加时费），不参与匹配，随报价单带出。**已实现（数据为虚构样例）。**
3. **交接字段校验**：按客户用途配置必填项、条件必填项与需专业确认项；缺少硬性需求、单位口径或原文证据时生成补问清单，阻止进入"交接完成"。**已实现。**
4. **空间匹配**：硬条件用确定性规则校验，区分满足、不满足和待核实；结果展示逐项依据与缺口。**已实现，尚未完成真实业务运行验收；"已填条件满足"不能解释为可交付承诺。**
5. **退回与复核闭环**：记录退回原因、责任人、补充信息及重新提交过程。支持接受、修改等级、修改解释、驳回、升级五种动作，每次记录操作者、时间、理由、引用版本和最终处理内容；驳回必须从 12 个退回原因枚举中选择代码，理由文本作附注。**已实现。**
6. **报价单 v2**：基于匹配结论生成报价单。服务端按需求卡当前字段对当前台账重跑匹配，只有"已填条件满足"或"条件满足但溯源不全"的房源可以生成。编号 `RJ-{YYYYMM}-{序号}`，同一需求卡 + 房源重复生成自动升版（首次报价 / 修订报价，修订必须给原因），旧版自动作废；条款含押金、免租、租期、物业费、年递增、装修与搬迁补贴、报价有效期，自动计算三年总占用成本；免租超 92 天或折扣超 5% 须管理员授权审批后才能发出；需求卡明确了承重或供电容量时，发出前须有对应专业确认。**已实现（草稿素材，不是正式承诺）。**
7. **脱敏、字段权限与审计**：模型调用前处理敏感信息，后端按角色控制字段可见性和操作权限；阻断项由获授权人员处理，业务人员不能自行解除专业审核阻断。审计日志独立留痕，逐条入 sha256 hash 链，接口返回链完整性校验结果。**已实现（角色由请求头声明，非真实认证）。**

## 启动与使用

本地运行。Python 3.10+，无第三方依赖，无需构建步骤。

```bash
python app.py
```

浏览器打开 http://127.0.0.1:8765 。Windows 下也可执行 `powershell -ExecutionPolicy Bypass -File scripts/start.ps1`。

### 工作台七步流程

页面采用左侧边栏导航，七个环节按二级分类收纳（需求侧：需求卡/访谈抽取/字段裁定；交接协作：交接校验与复核；房源与报价：台账/匹配与报价；审计与指标：审计留痕），一次只显示一个面板，顶部常驻当前需求卡上下文。

1. **需求卡**：新建需求卡并选择客户用途。用途决定哪些字段必填、哪些需工程或复核确认。列表支持关键词搜索、状态筛选与分页。
2. **访谈抽取**：粘贴访谈原文。默认本地规则抽取；配置模型后启用 AI 抽取，发送前自动脱敏。
3. **字段裁定**：逐项选择状态（已明确 / 未知待补 / 未提出要求 / 确认无此要求）并填写原文证据。空白的不同语义在此区分。
4. **交接校验与复核**：跑校验看阻断项与补问清单；有阻断项时提交会被拒绝。复核角色可执行五种复核动作，驳回时从下拉选择退回原因代码并附说明。
5. **载体参数台账**：导入房源 JSON。缺溯源信息的房源只作待核实素材；台账可另填报价参数（得房率、物业费、交付标准等）供报价单带出。
6. **空间匹配与报价**：硬条件匹配，展示逐项依据与缺口；匹配通过的房源可生成报价单草稿（编号、版本、三年总占用成本、有效期），超授权报价须管理员审批后发出，草稿可发出或作废。
7. **审计留痕**：逐条查看操作记录并展示 hash 链校验结果，可导出留痕报告；过程指标含状态分布与溯源完整率条形图。需求卡还支持导出 Markdown 汇总报告（匹配结论按当前台账重算）。

### 智能助手

页面右下角"智能助手"悬浮球展开对话抽屉。助手基于当前需求卡生成补问清单、状态总结、报价口径、字段口径与匹配结论解读；配置模型后（`AGENT_API_KEY` / `AGENT_MODEL`）自动切换为 AI 自由问答，发送内容先脱敏，模型不可用时回落规则模式。助手只读不改数据，因此不写审计留痕。

### 角色与权限

界面右上角切换当前角色，权限在后端校验：

| 角色 | 可做 | 不可做 |
| --- | --- | --- |
| 业务（招商） | 建卡、改字段、提交交接、导入台账、匹配、生成与流转报价单、导出报告 | 解除专业确认阻断、执行复核动作、审批超授权报价 |
| 工程 | 编辑、专业确认、台账核实、匹配、导出报告 | 生成报价单、执行复核动作 |
| 复核 | 提交、复核动作、专业确认、匹配、导出报告 | 生成报价单 |
| 管理员 | 全部（含超授权报价的授权审批） | — |

角色标识通过 HTTP 头传入，是本机演示用的轻量机制，不构成真实身份认证。进入真实试点前必须接入实际登录体系。

### 环境变量

默认采用规则抽取，仅识别明确数值与单位。配置兼容 Chat Completions 的模型服务可启用 AI 抽取：

| 变量 | 说明 |
| --- | --- |
| `AGENT_API_KEY` | 模型服务密钥。留空则使用本地规则抽取 |
| `AGENT_MODEL` | 模型名称 |
| `AGENT_BASE_URL` | 服务地址，例如 https://api.openai.com/v1 |
| `AGENT_HOST` / `AGENT_PORT` | 监听地址与端口，默认 127.0.0.1:8765 |
| `AGENT_DB` | 数据库路径，默认 data/agent.db |
| `AGENT_ACCESS_LOG` | 设为 1 时打印 HTTP 访问日志 |

访谈内容将发送至该模型服务（发送前脱敏）。密钥仅存于服务端环境。程序直接读取系统环境变量，不会自动加载 `.env` 文件。

任何 AI 抽取结果须人工确认。缺失房源参数不视为满足条件。面积按所需面积下限筛选；租金为元/平方米/月；电力为 kVA；承重为 kg/平方米；净高为米。面积上下限、行业准入、消防、交付日期暂由人工核实，不计入自动匹配通过条件。

## GitHub 项目借鉴与选型边界

以下信息来自报告截图，本次未联网复核仓库、许可证或维护情况，也未复制、安装或集成这些项目。正式采用前必须核验目标版本及其依赖授权。截图没有给出"五项成熟组件项目"的完整名称，此处不补造名单。

- [alvn1213/smart-park](https://github.com/alvn1213/smart-park)：参考房源、楼栋、线索、客户和合同的数据建模。报告称房源端存在层高字段，但需求端缺少硬件诉求字段；报告同时指出无 LICENSE，不能据此认定允许商用或直接复制代码，需要取得明确授权。
- [yingfengxinxi/YFPark](https://github.com/yingfengxinxi/YFPark)：参考招商、空间管理、BPM 审批、权限和操作日志。报告标注 Apache-2.0，采用前核验实际版本和依赖。客户需求仍缺层高、电力及承重等字段，不能直接替代本项目。
- [stemAGH/openestate](https://github.com/stemAGH/openestate)：参考地产 CRM 的客户、线索、房源与访问控制设计。报告标注 AGPL-3.0，修改、部署和对外服务前需评估相应义务。此前对话中的 `openstate` 为误写，此处按截图修正为 `openestate`。
- [n8n](https://github.com/n8n-io/n8n) 与 [Dify](https://github.com/langgenius/dify)：作为工作流和模型编排候选，按实际集成需要选择；两者不是本 MVP 的依赖。报告指出其许可并非标准 OSI 开源许可，对外服务等场景有约束，不能概括为允许任意商用分发。

组件选型围绕结构化抽取、规则层校验、脱敏、字段权限、审计留痕、人工兜底编辑六项能力展开。工作流工具不能替代后端权限校验、独立专业复核和真实载体参数台账。

## 分阶段实施

1. **当前阶段（已完成）**：需求抽取与人工修订、载体台账校验、硬条件匹配、交接校验与复核闭环（退回原因枚举）、报价单 v2（编号版本、三年总占用成本、让利授权审批、专业确认门槛）、审计 hash 链、报告导出。本地运行与 143 项规则测试通过。尚未在真实业务数据上运行验收。

3. **受控试点**：接入实际登录体系与权限矩阵，在统一口径下对比交接遗漏率，记录退回原因与节点耗时；意向转访率只观察。
4. **扩展**：根据试点结果决定是否接入现有园区系统及扩展报价、合同、交付流程。

## 已知限制

- 角色标识由请求头声明，不是真实身份认证，仅适用于本机演示。
- 报价单是草稿素材：押金、免租期、租期、物业费为默认商务条款；三年总占用成本与装修估算按行业参照值计算，需园区确认后才能对外；正式报价与价格审批不在本系统内。
- 未集成 CRM、录音转写、登录权限系统与真实客户档案。
- 房源台账目前只有虚构样例，不能用于真实招商。
- 系统提供的指标是过程计数，不等于业务交接遗漏率，业务口径须在试点前确认。
- 不要开放到公网。
