# 设计说明

## 一、问题与范围

依据用户提供的行业分析报告截图，本项目聚焦招商需求在交接过程中丢失的问题。报告定位了三个断点：面访时硬件诉求未落库、交接无字段校验、退回无痕。各节点耗时尚未分别测量，因此不将任何环节断言为"最耗时"。

业务流程：线索 → 需求访谈 → 空间匹配 → 报价 → 合同审核 → 交付。本项目当前范围为需求访谈、空间匹配、交接校验、复核闭环与报价单草稿 v2（含授权审批留痕）；合同审核与交付只预留接口，不属于已实现功能。

## 二、整体架构

```text
浏览器工作台 (web/)
      │  HTTP + JSON
      ▼
路由层 (api/routes.py) ─── 权限校验、脱敏、错误映射
      │
      ├── 抽取器 (extractors/)   规则抽取 + 模型抽取，输出统一 items 结构
      ├── 核心层 (core/)         matching 硬条件匹配 / handover 交接校验
      │                          / quotation 报价 v2：条款、三年成本、授权门槛
      ├── 台账层 (inventory/)    参数与溯源校验、报价参数校验、模板
      ├── 复核层 (review/)       五种复核动作与状态迁移、退回原因枚举
      ├── 安全层 (security/)     脱敏、角色权限、职责分离
      ├── 存储层 (storage/)      SQLite：需求卡、台账、复核、报价单、审计（hash 链）
      └── 配置 (config/defaults.json)  用途规则、角色权限、报价默认条款与授权额度
```

各层职责单一、可独立测试。所有规则判定都在后端，前端隐藏按钮不构成权限控制。

## 三、需求结构化

### 3.1 空白的三种业务语义

报告要求区分"未知值、未提出要求及确认无此要求"。这是本项目最重要的建模决定：

- `unknown`（未知待补）：客户提到过但没给准数 → 交接前必须补问
- `not_requested`（未提出要求）：本次访谈未涉及 → 交接前仍需客户确认
- `none_confirmed`（确认无此要求）：客户明确表示不需要 → 已有依据，记为提示项

如果沿用单一 `null`，系统无法区分"漏问了"和"客户说了不需要"，交接校验就退化成填表检查。这正是报告所指的"交接无字段校验"。

### 3.2 证据绑定

每个已明确取值都绑定一段原文引文（`evidence`）。模型抽取时，引文若不在原文中、或引用的是别的单位口径，该项自动降级为"未知待补"并阻断交接。降级而非拒绝，是为了不丢失人工线索，同时不让错误值进入匹配。

### 3.3 层高与净高

拆成 `height`（净高）与 `layer_height`（层高）两个独立字段。抽取器不会用层高推定净高；证据校验会拦截"层高"出现在净高字段的情形。

## 四、载体参数台账

台账 = 空间参数 + 溯源元数据（来源、核实人、核实日期、版本）。溯源不完整的房源不会被判为"已填条件满足"，只作为待核实素材。

这是把报告要求的"房源载体参数台账必须由业务及工程人员建设和核实"落到代码约束上：没有溯源的数值，即使正确也无法支撑交付承诺。

导入时拦截单位混填（kW 当 kVA、带单位文本、0 代替 null 等），避免错误参数在台账里沉淀后再被当作事实引用。

## 五、交接字段校验

校验分四层：

| 层 | 检查内容 | 阻断级别 |
| --- | --- | --- |
| 必填层 | 按客户用途配置的必填项是否有明确取值 | blocking |
| 条件必填层 | 条件触发的字段 | advisory |
| 语义层 | 已明确字段是否有原文证据；层高/净高、kW/kVA 口径是否混用 | blocking |
| 专业层 | 需专业确认的字段是否已由有权限角色确认 | blocking |

用途规则配置在 `config/defaults.json`，含每种用途的必填字段、条件必填字段及其触发条件、需专业确认字段、需补充确认的问题模板。

### 5.1 交接状态机

```text
draft（草稿）
  │  校验通过
  ▼
pending（待交接） ──接受──► handover（已交接）
  │
  └──驳回──► returned（已退回） ──补充后重新提交──► draft
  │
  └──升级──► escalated（已升级）
```

有阻断项时提交会被拒绝，并返回补问清单。`escalated` 状态下不允许直接完成交接。

### 5.2 五种复核动作

| 动作 | 目标状态 | 必填信息 |
| --- | --- | --- |
| 接受 | handover | — |
| 修改等级 | draft | field、level、理由 |
| 修改解释 | draft | field、explanation、理由 |
| 驳回 | returned | reason_code、理由 |
| 升级 | escalated | escalate_to、理由 |

驳回的 `reason_code` 必须从 12 个退回原因枚举中选取（硬件条件缺失/不匹配/未核实、容量参数缺失、面积不匹配、交付条件未确认、价格超限、让利超授权、版本冲突、送错材料/旧版材料、缺少依据或溯源、系统不可用），理由文本作附注。枚举化是为了让"退回无痕"变成可统计的结构化数据：试点时按代码归因，而不是事后阅读自由文本。`GET /api/config` 把枚举下发给前端做下拉；复核历史同时展示代码与文案。

每次动作留痕：操作者、角色、时间、理由、引用版本、最终处理内容。引用版本用于回答"当时交接的是哪一版需求"。

## 六、报价单 v2

### 6.1 编号、版本与轮次

每张报价单有全局递增编号 `RJ-{YYYYMM}-{序号}`。同一需求卡 + 房源再次生成时自动升版：`quote_version` 加 1，轮次从"首次报价"变为"修订报价"，修订必须填写至少 4 字的修订原因；上一版（非作废）自动置 `voided`。版本链回答"这单报过几版、为什么改"，与需求卡 `ref_version` 的引用留痕同属一个口径。编号、版本计算与旧版作废在同一事务锁内完成，失败时不落任何行。

### 6.2 三年总占用成本

报价条款不只是月单价，客户决策看的是三年总账：

```text
计租面积   = 登记面积 × 得房率（台账缺得房率按 100%，写入 assumptions）
三年租金   = 月单价 × 计租面积 × 12 × (1 + (1+递增) + (1+递增)²)
三年物业费 = 物业费 × 计租面积 × 36
装修投入   = 装修单价 × 计租面积（单价按交付标准查表估算，可人工覆盖）
总占用成本 = 三年租金 + 三年物业费 + 装修投入 − 装修补贴 − 搬迁补贴
```

装修单价查表按交付标准：L1 300–600、L2 100–300、L3 0–30、毛坯 300–800 元/㎡（取中值）。这些是行业参照值，配置在 `config/defaults.json` 的 `quotation.renovation_cost_per_sqm`，每处引用都标注"行业参照，需园区确认"，报告导出同样带出。台账未登记物业费时按 0 计入并提示，不静默当作无物业费。

### 6.3 让利授权与发出门槛

报价单发出（issue）有两道服务端门槛，前端隐藏按钮不是控制：

- **让利授权**：免租天数超授权额度（默认 92 天）或单价折扣超授权（默认 5%，相对台账租金计算）的报价单，`terms.requires_approval` 置真，直接发出返回 409；须管理员调用授权审批接口记录审批人与时间。业务人员不能自我审批，额度可在 `quotation.authority` 配置。
- **专业确认附页**：需求卡明确了承重或供电容量时，发出前对应字段必须已有有效专业确认。这与交接校验的专业确认门槛是同一机制的延伸：报出去的数字背后要有工程依据。

### 6.4 台账报价参数（不参与匹配）

台账另设六个仅用于报价的参数：得房率、物业费、交付标准、净高、供电冗余、空调加时费。它们不参与硬条件匹配（匹配口径不变），导入时同样做范围与枚举校验。区分"匹配参数"与"报价参数"是刻意设计：匹配错一个参数会导致漏掉房源，而报价参数只影响算钱，两者更新频率和责任角色不同。

## 七、脱敏、权限与职责分离

### 7.1 脱敏

模型调用前对访谈文本做脱敏（手机号、身份证、统一社会信用代码、邮箱、卡号等），只发掩码文本到外部服务。响应中带 `redacted` 标记，便于前端告知用户内容已被处理。

### 7.2 角色与职责分离

| 角色 | 关键权限 | 不可做的事 |
| --- | --- | --- |
| 业务（招商） | 建卡、改字段、提交交接 | 不能解除专业确认阻断、不能执行复核动作 |
| 工程 | 编辑、专业确认、台账核实 | 不能执行复核动作 |
| 复核 | 提交、复核动作、专业确认 | — |
| 管理员 | 全部 | — |

"上传资料的业务人员不得自行解除专业审核阻断"在代码里由 `require_professional_clearing` 强制：业务角色调用专业确认接口直接返回 403。

角色标识通过 HTTP 头 `X-Actor-Role` 传入。当前实现是本机演示用的轻量机制，不构成真实身份认证；进入真实试点前必须接入实际登录体系。

## 八、持久化与审计

SQLite 存六类数据：需求卡、房源台账、复核动作、专业确认、报价单、审计日志。审计日志与业务表分离，记录操作者、角色、动作、引用版本与时间戳。

审计表逐条入 sha256 hash 链：每条记录计算 `hash = sha256(prev_hash + 规范化 JSON)`，`prev_hash` 取上一条的 `hash`。接口按全表重算返回 `chain_valid`，任何一条被篡改或删除都会使后续校验失败。旧库迁移来的历史记录（无 hash）不参与校验，避免误报。hash 链能发现篡改但不能阻止篡改，权威留痕仍以数据库备份为准。

导出的报告是留痕快照，不等于独立审计留痕——真正的审计依据是 `audit` 表的逐条记录。

## 九、当前不具备的能力

以下为本项目尚未实现、试点前必须补齐的部分：

- 真实登录与身份认证（当前角色由请求头声明）
- 录音转写与 CRM 集成
- 真实园区台账数据采集
- 交接遗漏率的正式统计（系统提供过程计数，业务口径须另行确认）
- 节点耗时采集
- 正式对外报价与价格审批流程（系统内为草稿与授权审批留痕）、合同审核与交付流程

## 十、验收口径提示

报告的一级验收目标是"需求交接遗漏率从 22% 降至 8%"。这是报告基线与目标，不是本原型已经取得的效果。试点前须确定遗漏率的统计单位、分母、抽样范围、时间窗口与复核责任人，并复核 22% 基线；不能用字段填写率替代交接遗漏率。
