# 融景园区 · 报价单设计方案

**设计对象**：商业租赁与空间交付主流程第 04 环节「报价」的输出物
**设计依据**：《融景园区行业分析报告》§1.3 内部现状诊断、附录 B「AI 应用边界」；访谈事实 f00 / f01 / f20 / f22 / f40 / f41 / f44
**版本**：v1.0（2026-11-01）
**性质**：设计方案，非已生效的报价模板。定价参数、让利额度、审批人姓名均待确认

---

## 一、这份报价单要解决什么问题

现状下的报价单有三个具体毛病，它们和报告里的三个断点一一对应：

| 现状问题 | 表现 | 对应断点 |
|---|---|---|
| **只写面积和租金** | 报价单上只有面积、租金、物业费，客户提出的层高、电力容量、承重条件不在报价口径内 | 断点① |
| **不是报价依据** | 报价时拿不到硬件条件，只能按面积和租金推算；到了空间匹配与合同审核才发现不符，反复退回 | 断点②③ |
| **版本与责任不清** | 报价单发给客户后仍在改，园区不知道哪一版是有效的；旧版还在发送 | 断点③ |

行业侧的原因很清楚：2026 年上海高端商务空间已进入买方市场，租户把谈判从单价推进到**免租期、交付状态、物业费、空调加时费、车位、恢复原状责任和扩租条件**——两处办公室每平方米每天只差几角钱，三年后真实成本仍可能拉开一大截。**报价单如果只写面积和租金，客户根本无法做比较**，招商人员在谈判中反复压价的原因就在这里。

所以这份报价单的设计目标不是"更好看"，而是三件具体的事：

1. **硬件条件进入报价口径** —— 让报价成为可比较、可承诺的载体，而不是只有价格没有条件
2. **报价单版本唯一且可追溯** —— 客户手上的、园区手上的、合同引用的，是同一版
3. **报价不越权** —— 报价单是对外沟通文件，不构成承诺；承诺只在合同，且须由审批人确认

## 二、报价单总体结构

### 2.1 单页分区的整体版式

```
┌─────────────────────────────────────────────────────────────┐
│ ① 抬头区　园区名称 · 报价单编号 · 版本号 · 出具日期 · 有效期  │
├─────────────────────────────────────────────────────────────┤
│ ② 客户与项目区　客户主体 · 对接人 · 项目编号 · 报价轮次     │
├─────────────────────────────────────────────────────────────┤
│ ③ 载体与硬件条件区　空间标识 · 层高 · 净高 · 电力 · 承重 …   │  ← 报价的核心
│    ├ 3.1 空间基础信息                                    │
│    └ 3.2 硬件条件与技术参数                              │
├─────────────────────────────────────────────────────────────┤
│ ④ 费用明细区　租金 · 物业费 · 免租期 · 递增 · 押金 · 补贴   │
├─────────────────────────────────────────────────────────────┤
│ ⑤ 三年总占用成本区　含一次性投入与隐性成本                 │  ← 客户真正比的东西
├─────────────────────────────────────────────────────────────┤
│ ⑥ 交付条件区　交付状态 · 交付时间 · 装修与报建 · 配套     │
├─────────────────────────────────────────────────────────────┤
│ ⑦ 专业确认附页区　承重/消防确认结论 · 签署人 · 确认时点     │  ← 条件不具备则不报价
├─────────────────────────────────────────────────────────────┤
│ ⑧ 说明与效力区　报价性质 · 有效期 · 变更机制 · 联系方式   │
└─────────────────────────────────────────────────────────────┘
```

**设计要点**：③ 硬件条件区与 ④ 费用明细区**必须同页呈现**。把条件与价格拆到两页，等于让客户在比价时忽略条件——这正是现状报价单失效的机制。

### 2.2 与主流程的对应

| 报价单分区 | 数据来源 | 来源岗位 | 是否需专业确认 |
|---|---|---|---|
| ② 客户与项目区 | CRM 线索与需求记录 | 招商经理 | 否 |
| ③ 载体与硬件条件区 | **载体参数台账** | 园区服务经理维护 | **是**（承重、层高、消防） |
| ④ 费用明细区 | 定价规则 + 授权额度 | 招商经理 | 否（超出额度须审批人） |
| ⑤ 三年总占用成本 | 系统按 ④ 与 ⑥ 自动计算 | 系统 | 否 |
| ⑥ 交付条件区 | 交付标准 | 园区服务经理 | 否 |
| ⑦ 专业确认附页 | **专业确认独立附件** | 专业确认人 + 审批人 | **是** |
| ⑧ 说明与效力区 | 固定模板 | 法务/合同审核专员审 | 否 |

**关键设计**：③ 与 ⑦ 的数据源不同——③ 来自台账（园区侧客观参数），⑦ 来自专业确认（针对本次客户需求的专业判断）。两者不能合并，因为只有 ⑦ 能支撑对客户的承诺。

## 三、逐区字段设计

### ① 抬头区

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| 园区名称 | 文本 | ✓ | |
| 报价单编号 | 编码 | ✓ | 唯一，建议 `RJ-{园区码}-{YYYYMM}-{序号}` |
| **版本号** | 编码 | ✓ | `V1 / V2 / V3`，每次修改递增，**旧版自动作废** |
| 出具日期 | 日期 | ✓ | |
| **有效期** | 日期 | ✓ | 默认 15 天；过期须重新出具 |
| 出具人 / 联系方式 | 文本 | ✓ | 客户唯一对接窗口 |

> **版本号是这份设计里最不起眼但最关键的一栏。** 现状下园区不知道哪一版报价是有效的（断点③），版本号 + 唯一编号 + 旧版自动作废，是成本最低的解法。

### ② 客户与项目区

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| 客户主体名称 | 文本 | ✓ | |
| 客户统一社会信用代码 | 文本 | ✓ | |
| 联系人 / 联系方式 | 文本 | ✓ | **按权限可见**：报价单发出后客户方联系信息通常需脱敏 |
| 项目编号 | 编码 | ✓ | 关联 CRM 线索与需求记录 ID |
| **报价轮次** | 枚举 | ✓ | `首次报价 / 修订报价 / 复议报价` |
| 关联报价单编号 | 编码 | 修订时必填 | 修订时指向被修订的上一版 |
| **修订原因** | 枚举 + 文本 | 修订时必填 | 见第五章退回原因枚举 |

### ③ 载体与硬件条件区（核心）

**3.1 空间基础信息**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| 楼栋 / 楼座编号 | 编码 | ✓ | |
| 楼层 / 房号 | 文本 | ✓ | |
| 建筑面积（㎡） | 数值 | ✓ | |
| 得房率（%） | 数值 | ✓ | 客户实际可用面积 ≠ 建筑面积 |
| 交付状态 | 枚举 | ✓ | `毛坯 / L1 简装 / L2 标准精装 / L3 超级办公室` |
| 平面图版本号 | 编码 | ✓ | 与图纸唯一对应 |

**3.2 硬件条件与技术参数** —— 这一组是本次设计的核心新增内容

| 字段 | 类型 | 必填 | 说明 | 专业确认 |
|---|---|---|---|---|
| 结构层高（m） | 数值 | ✓ | | 否（台账值） |
| 净高（m） | 数值 | ✓ | 层高扣楼板、架空地板、吊顶、消防喷淋后的实际可用高度 | 否（台账值） |
| 标准层荷载（kg/㎡ 或 kN/㎡） | 数值 | ✓ | | **是** |
| 电力容量（kW） | 数值 | ✓ | | **是** |
| 配电冗余 | 枚举 | ✓ | `单路 / 双路 / 双路+应急电源` | **是** |
| 空调系统 | 文本 | ✓ | 含加班加时机制与费用（如 500-1500 元/小时） | 否 |
| 独立卫生间 / 茶水间 | 枚举 | ✓ | | 否 |
| 电梯配比与等候时间 | 文本 | ✓ | 参考门槛：等候 ≤30 秒、≥1 部/5000㎡ | 否 |
| 车位配比 | 文本 | ✓ | 参考门槛：≥1 个/200㎡ | 否 |
| 光纤与多运营商接入 | 枚举 | ✓ | | 否 |
| 新风 / 空气质量 | 文本 | ○ | | 否 |
| 消防系统等级 | 枚举 | ✓ | | **是** |
| **客户特殊条件** | 文本 | ○ | 客户提出的其他硬性要求，逐条列明 | 视情况 |

> **必填规则**：标 ✓ 的字段**任一为空，报价单不得出具**。这是把断点①的修复前移到报价环节——如果报价单上能出现"层高：待定"，那它就退回了现状。
>
> **得房率为什么单列**：客户真正付租金的是可用面积，不是建筑面积。行业里 76% 得房率（中海国际中心标准层）与 100% 之间差出的 24%，直接改变客户的单位成本判断。不写清楚，报价单无法支撑三年总成本比较。

### ④ 费用明细区

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| 租金单价（元/㎡/天） | 数值 | ✓ | |
| 计租面积（㎡） | 数值 | ✓ | 建筑面积 × 得房率 |
| 月租金（元） | 数值 | ✓ | 系统按前两项计算 |
| 物业费（元/㎡/月） | 数值 | ✓ | |
| 空调加时费标准 | 文本 | ✓ | 即使本次不适用也要列，避免入驻后争议 |
| **免租期** | 数值 + 文本 | ✓ | 免租月数 + 是否含物业费 |
| **租金递增** | 数值 + 文本 | ✓ | 递增方式 + 周期 |
| 押金 | 文本 | ✓ | 金额 + 退还条件 |
| **装修补贴 / 搬迁补助** | 数值 | ○ | 行业标配让利条件 |
| 其他费用 | 文本 | ○ | |

> **让利条件必须显式列出**。行业侧业主让利已是免租期 3-6 个月标配并叠加装修补贴与搬迁补助，58% 租户在成本降 20%-50% 时考虑搬迁——**不写清楚，双方对"让了多少"的判断完全不同**，这恰恰是压价与内卷的来源之一。

### ⑤ 三年总占用成本区（让客户能真正比较）

这一区是让报价单"可用"的关键。客户真正比的不是单价，是三年总账。

| 项目 | 数据来源 | 说明 |
|---|---|---|
| 三年租金合计 | ④ 计算 | 含递增 |
| 三年物业费合计 | ④ 计算 | |
| 三年空调加时费预估 | ⑥ 条件 + 客户规模 | 按客户实际人数与加班频次估 |
| 一次性装修投入 | ⑥ 交付状态 | 参照：L1 约 300-600 元/㎡、L2 约 100-300 元/㎡；毛坯入驻周期 2-3 个月、投入 30-80 万元 |
| 搬迁成本 | ④ 押金/退租责任 | 含恢复原状责任 |
| **三年总占用成本** | 汇总 | 客户决策口径 |

> 行业参照：两处办公室每平方米每天只差几角钱，三年后真实成本仍可能拉开一大截。**报价单如果不能支撑这个比较，就只是一张价格表。**

### ⑥ 交付条件区

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| 可交付日期 | 日期 | ✓ | |
| 交付状态 | 枚举 | ✓ | 与 ③ 3.1 一致 |
| 装修报建协助 | 枚举 | ✓ | 是否提供报建协同 |
| 空调加时开通 | 枚举 | ✓ | |
| 网络开通时限 | 文本 | ✓ | |
| 园区配套清单 | 文本 | ○ | 餐饮、班车、会议室等 |

### ⑦ 专业确认附页区（条件不具备则不报价）

**这是报价单的硬门槛，不是可选项。**

| 字段 | 必填 | 说明 |
|---|---|---|
| 确认事项 | ✓ | 承重 / 消防 / 其他 |
| 确认结论 | ✓ | 满足 / 不满足 / 有条件满足 |
| 确认依据 | ✓ | 计算书编号、图纸编号或现场核查记录编号 |
| **签署人** | ✓ | 专业确认人姓名与岗位（不是"公司"） |
| **确认时点** | ✓ | 精确到日期 |
| 确认所依据的载体编号与版本 | ✓ | 与 ③ 的楼栋/房号/平面图版本对应 |
| 备注条件 | ○ | 有条件满足时的限制说明 |

**设计规则**：
- ⑦ 未完成签署，**报价单不得进入发放环节**，系统层面阻断
- ⑦ 引用的载体编号与版本必须与 ③ 一致；③ 改版则 ⑦ 失效并须重签
- ⑦ 作为**独立附件**存在，不与报价单正文合并 —— 这是报告中 REQ-2 明确指向的形态

> **为什么必须是"签署人"而不是"公司"**：报告里傅景的原话是"涉及最终决定、对外承诺或资产变更，要由对应审批人确认，不能借用其他人的账号"。落到报价单上就是——**结论必须能追溯到具体的人和时间**，否则客户手上这份报价在合同审核阶段不被采信。

### ⑧ 说明与效力区（固定模板，法务审）

固定条款内容要点：

1. **报价单性质**：本报价单为商务沟通文件，**不构成租赁合同、不可作为合同承诺依据**；最终权利义务以正式合同为准
2. **有效条件**：报价以专业确认结论成立为前提；专业确认结论变化时，报价自动失效
3. **版本效力**：以园区系统内最新版本为准；此前版本自动作废
4. **有效期**：超过有效期须重新出具
5. **不可承诺事项**：承重、消防等须专业确认的条件，报价单不得单方面承诺
6. **变更机制**：任何变更须重新出具报价单并递增版本号，不得口头或邮件附加修改

> **第 3 条与第 6 条是现状最缺的。** 现状下报价单发出后仍在改、两个版本冲突、缺依据，都指向同一件事：没有一个"以哪一版为准"的规则。这两条是纯管理约定，不花钱，但能直接消灭一整类争议。

## 四、报价单与合同的关系：边界要写死

这是设计方案里最需要提前说清的一件事。行业合同智能体的实践反复指向同一个道理——**"已确认"但没有留痕，是审核最怕看到的**。

| 事项 | 报价单可以做 | 报价单不可以做 | 承诺的载体 |
|---|---|---|---|
| 硬件条件 | 列示台账客观参数 | 承诺"一定能满足 X 承重" | 合同条款 + ⑦ 专业确认 |
| 价格 | 列示单价、免租期、补贴 | 承诺超出授权额度的让利 | 合同 + 审批人确认 |
| 交付状态 | 列示交付标准与日期 | 承诺未获专业确认的工程条件 | 合同 |
| 客户联系方式 | 按权限可见 | 传给无权限岗位 | — |

**版本关系示意**：

```
需求记录（结构化）→ 空间匹配 → 报价单 V1
                                    ↓ 客户反馈
                              报价单 V2（关联 V1，填修订原因）
                                    ↓ 客户确认
                              合同起草
                                    ↓
                        引用报价单 V2 的具体版本号 + ⑦ 专业确认附页
                                    ↓
                              合同审核（傅景核验版本与附页）
```

合同中**必须引用报价单的版本号**，而不是"参照报价单"。这是让"版本唯一出口"真正生效的动作。

## 五、退回原因枚举（支撑断点③修复）

现状下报价反复退回，但**退回原因不可统计** —— 报告已明确这是断点③。报价单的出具流程必须把退回原因结构化，否则数据永远出不来。

### 5.1 退回责任方

| 代码 | 责任方 | 说明 |
|---|---|---|
| REQ-NEED | 需求访谈（招商经理） | 客户需求未记录完整 |
| REQ-MATCH | 空间匹配（租赁运营专员） | 载体与需求不匹配 |
| REQ-PRICE | 定价规则（招商经理/财务） | 报价超出规则或授权 |
| REQ-CONFIRM | 专业确认（专业人员） | 专业确认结论不满足或未完成 |
| REQ-DOC | 版本与资料（园区服务经理） | 版本冲突、资料缺失、旧资料在发 |

### 5.2 退回原因枚举（枚举值必须落库）

| 代码 | 含义 | 典型处置 |
|---|---|---|
| `HW_MISSING` | 硬件条件字段为空 | 回填后重出 |
| `HW_MISMATCH` | 硬件条件与载体不符 | 重新匹配载体 |
| `HW_UNVERIFIED` | 硬件条件未经专业确认 | 补 ⑦ 附页 |
| `CAPACITY_MISSING` | 载体参数台账无该楼栋数据 | 台账补录 |
| `AREA_MISMATCH` | 面积/得房率口径不一致 | 统一口径 |
| `DELIVERY_UNCONFIRMED` | 交付状态与实际不符 | 现场核实 |
| `PRICE_OVER_LIMIT` | 超出定价规则或授权额度 | 申请审批 |
| `INCENTIVE_ABOVE_AUTH` | 让利条件超出授权 | 申请审批 |
| `VERSION_CONFLICT` | 与既有版本冲突 | 作废旧版 |
| `OLD_MATERIAL_SENT` | 旧宣传资料仍在发送 | 停止发送 + 回收 |
| `MISSING_BASIS` | 缺少依据 | 补依据 |
| `SYSTEM_UNAVAILABLE` | 关键系统不可用 | 转人工 |

### 5.3 记录要求（每次退回必填三要素）

| 要素 | 要求 |
|---|---|
| **退回原因** | 从上述枚举中选择（单选主因，可选附注） |
| **接手人** | 具名，不能是岗位代称；由规则指定而非随意填写 |
| **确认时间** | 以系统时间为准，不接受手工填写 |

> 这三项正是傅景提出的红线原文：**"需要标注触发原因、接手人和确认时间，不能只给一句模糊提醒"**。报告里已指出"接手人不明确时，卡顿就发生在交接环节，而不是审核环节"——所以接手人必须由规则指定，不能留空。

### 5.4 与节点耗时测量的关系

报告的 REQ-5 要求按节点统计退回次数与原因。**这份枚举就是统计口径的起点** —— 没有枚举，退回原因只能靠自由文本，永远无法聚合分析。建议在阶段 0 的人工测量期就并行使用这套代码，用最笨的办法把第一批数据攒出来。

### 6.1 报价流程（衔接 AI 赋能后的目标态）

| 步骤 | 动作 | 责任 | AI 可否承担 | 卡点 |

| 3 | 报价草稿生成 | 系统 | ✓ 套模板与定价规则 | — |

| 5 | **专业确认附页签署** | 专业确认人 + 审批人 | ✗ **不可自动化** | **未签署 → 阻断** |

| 让利项 | 建议授权层级 | 备注 |

| 免租期 ≤ 1 个月 | 招商经理 | 自行决定 |
| 免租期 1-3 个月 | 招商经理 + 园区负责人 | 行业标配区间为 3-6 个月 |

### 6.3 三条红线在报价环节的落地

| 红线 | 报价单中的具体落地 |
|---|---|
| **权限红线**（f41） | 报价单发出后，客户联系方式在园区侧按权限可见；免租期与折扣的最终决定须对应审批人确认，不得由无授权人代签 |
| **专业确认红线**（f40） | 报价单 ⑦ 区未签署不得发放；报价单不得单方面承诺承重、消防条件；客户联系方式限制使用规则须在报价单发出前生效 |
| **人工兜底不可静默**（f44） | 报价流程中任何转人工（台账无数据、专业确认不满足、超授权）须标注触发原因、接手人、确认时间 |

## 八、落地路径

### 8.1 三步走

| 阶段 | 动作 | 产出 | 依赖 |
|---|---|---|---|
| **第一步：先定义，不开发** | 定字段清单、退回原因枚举、让利授权额度、专业确认附页格式 | 本方案定稿版 | 顾明岚（授权额度）、傅景（附页格式） |
| **第二步：人工试用** | 在试点园区人工按新格式出报价单，用真实案例跑 | 首批退回原因数据 | 载体参数台账（最小版） |
| **第三步：系统化** | 报价单生成、版本管理、校验规则、附页留痕 | 报价单模块 | 上述两步的验证结果 |

> **强烈建议不要跳过第二步。** 报告的核心判断是"先测量、后切入"——报价单也一样，先用人工跑通字段与枚举，验证哪些字段真的会被填、哪些退回原因真的会发生，再决定哪些交给规则层、哪些交给模型层。

### 8.2 与主流程试点的关系

| 报告中的需求 | 本方案的对应 |
|---|---|
| REQ-1 硬件条件结构化留痕 | ③ 区 3.2 硬件条件字段清单 —— **报价单是这条需求的天然验证场** |
| REQ-2 专业确认留痕载体/签署人/节点 | ⑦ 区 —— 报价单强制要求签署人与时点，是 REQ-2 的第一个落地场景 |
| REQ-3 转人工触发清单与接手人 | 第五章退回原因枚举 + 三要素记录 |
| REQ-5 节点耗时测量 | 报价环节的退回次数与原因是阶段 0 测量的一部分 |
| REQ-6 客户关注点分布 | 报价单字段可扩展为"客户实际最关注哪一项"的留痕点 |

> **一个额外价值**：报价单是"客户真正关心什么"的最佳观测现场。行业数据显示客户关注点排序没有可引用的调研数据（招商经理原话），而报价单上客户逐条追问的字段，就是最硬的偏好数据。**建议在报价单上记录"客户对哪些字段单独提出追问"，作为 REQ-6 的第一批数据。**

## 附：设计原则总结

1. **条件与价格必须同页** —— 拆开等于让客户在比价时忽略条件
2. **必填字段宁可少，不可松** —— 出现"待定"就是退回现状
3. **版本号 + 唯一编号 + 旧版自动作废** —— 消灭"以哪一版为准"的争议，成本最低
4. **报价单不构成承诺** —— 承诺只在合同，且须审批人确认
5. **专业确认附页是硬门槛** —— 未签署不得发放，不是可选项
6. **退回原因必须枚举化** —— 自由文本永远无法统计
7. **接手人由规则指定，不靠自觉** —— 否则卡顿只是从审核转移到交接
8. **先人工跑通，再系统化** —— 字段和枚举本身也需要验证
